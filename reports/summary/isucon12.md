- **Project started 2026-09-24.** CloudFormation stack `isucon12-qualify` created from `isucon_cf_provisioning/isucon12_qualify/cf-template-isucon12-qualify.yaml` (profile `isucon15.prep`). 3 x c5.large (2 vCPU / 3.6 GB), same AMI, private IPs .11/.12/.13. Per the user: s3 = bench + pprotein (+ netdata parent), s1/s2 load-targeted, a 4th instance only if needed; splitting roles across the provisioned hosts needs no approval (standing authorization), scaling up is never allowed.
- App facts: Go + echo, run by docker compose (`go run` inside a container) on the AMI. Admin data (tenant, id_generator, visit_history ~3M rows) is in MySQL; each tenant's competition/player/player_score is a SQLite file (`tenant_db/<id>.db`, copied from `initial_data/` by `POST /initialize`; tenant 1 is 126 MB / 1.67M player_score rows). Concurrency control is a per-tenant `flock`.
- Infra set up: ansible (`isucon_ansible`, inventory switched to user `isucon` / key `isucon_id_rsa`, pprotein on s3, netdata parent on s3, pprotein-agent + netdata kickstart on s1/s2), git checkout of the new repo at `/home/isucon` on s1/s2, Go 1.23.4 at `/home/isucon/local/golang`, isuports now a native systemd unit (no docker), nginx LTSV access log and MySQL slow log (`long_query_time=0`) always on, pprotein pprof/httplog/slowlog targets, `/initialize` triggers the pprotein collect (Duration 90 s to cover prepare + the 60 s load).
- Gotcha hit: `deploy.sh` truncating a not-yet-existing `mysql-slow.log` created it root-owned, MySQL could not open it and silently switched `slow_query_log` OFF. Fixed (files are created with daemon-writable ownership first). Verify `SHOW VARIABLES LIKE 'slow_query_log'` after any deploy that touches logs.
- **Baseline (2026-09-24)**: pristine reference app (docker, no logging) `pass=true`, `score=2586`, 0 errors. With logging + pprotein on (native binary, commit `249cb15`): `pass=true`, `score=1834`. alp: ranking avg 2.47 s (sum 1010 s), player detail avg 1.74 s, score POST avg 3.4 s, admin billing avg 17.9 s. slp: `visit_history` GROUP BY (no index on competition_id) 136 s, `REPLACE INTO id_generator` 7018 calls 123 s, initialize's `DELETE FROM visit_history WHERE created_at >= ..` 4.8 s. pprof: only ~21% CPU busy, ~80% of samples in SQLite (`sqlite3_step`, full scans of `player_score`) — waiting on locks/IO, not CPU-bound.

- **Two experimental branches trialed on real hardware, 2026-09-29** (user request: try both ideas — an in-request trace and a way to recover the bench's per-actor API call sequence — each on its own branch off `main`). Stack recreated from the already-tracked 4-host template (same private IPs, new public IPs — see `config/isucon12.yaml`); recreation verified against the pre-teardown baseline (`pass=true`, `score=236455`, in range). Full steps, gotchas (ansible `repo` role missing `git` upstream tracking; Go 1.23.4 not on the fresh AMI and not automated anywhere, had to be reinstalled manually) and results in `reports/iterations/iteration-isucon12-observability-20260929.md`. Summary: **both worked as intended and neither broke the bench.** `experiment/request-tracing` (commit `5e33967`) adds an opt-in (env-var-gated, like the existing `sqltrace.go`) per-request span tracer — zero measurable cost when off, but **~8% score cost when on** (175k trace lines/run), so treat it as a manual-investigation tool only, never left on for a scored run; when on, it correctly pinpointed `billingReportByCompetition` as the dominant span inside the billing handlers. `experiment/actor-transition-trace` (commit `612c5e9`) tags each response with an `X-Isucon-Actor` header (reusing `parseViewer`'s already-decoded role/tenant/playerID, no extra cost) logged via one new nginx LTSV field; `scripts/actor_transitions.py` then reconstructs per-actor API call sequences from the access log alone — verified against a real 188k-line/9668-actor log, correctly recovering the organizer's add→score→finish→billing loop and the player's competitions→ranking↔player-detail loop, at negligible score cost (230438 vs baseline). Both branches were reverted back to `main` after verification (final check: `pass=true`, `score=230396`) and pushed to origin (`experiment/request-tracing`, `experiment/actor-transition-trace`) — neither is merged; ready to merge if the user wants either as standing tooling.
