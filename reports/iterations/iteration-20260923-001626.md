# Iteration 2026-09-23 00:16:26

## Agents Used

- Sub-agents were not used because: this was a tightly-coupled, single-hypothesis change requiring immediate live benchmark feedback, and it was rejected within one benchmark run — there was no analysis phase to delegate before the result made the decision obvious.

## Hypothesis

Following the previous iteration's finding (1 of 6 post-split runs failed with `CODE=32`, theorized as the matcher's fixed one-match-per-0.5s-tick rate no longer being paced by `s1`'s (now-relieved) CPU bottleneck), the hypothesis was: looping the existing single-match logic up to 20 times per `internalGetMatching` call (still fully sequential, no new concurrency, same selection order and chair-freeness check) would drain backlogs during bursts and eliminate `CODE=32` without introducing correctness risk.

## Change

`webapp/go/internal_handlers.go`: refactored the single match into `matchOneRide()` and called it in a loop up to `maxMatchesPerCall = 20` times per request. Commit `de2f88f`.

## Verification

- Local build/vet: clean. Deployed to `s1` (via `HOSTNAME=s1 deploy.sh` workaround), all services active.
- **Benchmark run 1: `pass=false`, score 10802, errors `map[1:158 2:9 3:10 7:7 8:6 13:2 17:2 21:2 22:1 25:6 30:1]`** — aborted with "発生しているエラーが多すぎます" (too many errors occurred). Time-to-match satisfaction actually went to 0% dissatisfied (matching got very fast), but many unrelated error categories fired simultaneously across many different codes.

## Decision

**Rejected immediately, reverted without further testing.** The failure pattern (many different, unrelated error codes firing simultaneously, "too many errors" abort) is a signature of general system overload/instability, not a single logic bug. Working theory: the fixed one-match-per-tick rate wasn't just pacing the matcher — it was implicitly throttling the *entire downstream system's* concurrent active-ride load (how many chairs are simultaneously mid-ride, sending coordinate updates, polling notifications, etc.). Jumping straight to a 20x burst-drain capability let a backlog release all at once, spiking concurrent load far beyond what the app/DB can sustain in steady state, rather than smoothly increasing average throughput. This is a good example of why the project's own guidance to change one small thing at a time applies even within a single "fix" — a 20x step was too aggressive to test as a single hypothesis.

Reverted via `git revert de2f88f` (commit `ebd6765`), redeployed, and re-verified: `pass=true`, score `5506`, `errors=map[]`. System confirmed back to the known-stable post-DB-split state.
