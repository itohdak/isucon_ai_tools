## Hypothesis

Two independent, evidence-backed candidates from the loop-start dispatch:

1. **(REJECTED)** `fillUserResponse` (called on nearly every hot path that embeds a `User` — livestream owner, livecomment author/reporter, reaction user) fetches the full icon image BLOB and runs `sha256.Sum256` over it on every single call, purely to compute `IconHash`. Precomputing and storing `icon_hash` at write time (`postIconHandler`) and selecting just that small column instead should cut both DB payload and app CPU.
2. **(ACCEPTED)** `getLivecommentReportsHandler`'s report-listing loop crashes with a 500 for the *entire* request when any one report row points at a livecomment already deleted by moderation (`moderateHandler` deletes `livecomments` rows but never touches `livecomment_reports`, and there's no FK/cascade). Skipping the orphaned row instead of erroring is a low-risk, docs-confirmed-safe fix.
3. **(ACCEPTED, added after the bisection)** `ng_words(livestream_id)` has no usable index — `moderateHandler`'s `SELECT * FROM ng_words WHERE livestream_id = ?` full-scans ~14k rows every call. Directly reduces mysqld's own CPU per already-issued query, on the host the Resource Monitor Agent confirmed is CPU-bound.

## Evidence

- Fresh 4-agent parallel dispatch at loop start (see Agents Used table).
- A benchmark run just before this iteration confirmed the recorded baseline still holds: `score=27215, pass=true` at commit `6be450f`.
- **Bisection evidence for the rejected icon_hash change** (all against the same commit range, same environment, back-to-back):
  - Full new code (icon_hash change + report fix), commit `8642c2a`: **15880**, **17682** (2 runs). App journal showed a burst of `context canceled` errors and multi-second latencies around one point in each run, plus the well-known pre-existing `POST /api/icon` deadlock (`Error 1213 (40001)`).
  - A/B, code reverted to `6be450f` (live-only revert, not committed): **25090** (1 run) — recovered to near the pre-iteration baseline.
  - A/B, only the report-fix redeployed (old `user_handler.go`, new `livestream_handler.go`, live-only): **26034** (1 run) — also recovered, isolating the icon_hash change as the specific regression source (not the report fix, not general environment drift).
  - SQL Agent's follow-up full slowlog ranking (spanning the mixed A/B window) showed the new `SELECT icon_hash FROM icons WHERE user_id=?` query was in fact ~8x cheaper per call than the old `SELECT image ...` (0.0002s vs 0.0016s avg) — confirming the regression was *not* due to the new query itself being slow. Working theory: freeing up app-side (s1) CPU that wasn't the bottleneck let the app submit more concurrent work to the already CPU-saturated s2 faster, without reducing s2's per-query CPU cost, worsening contention (SQL Agent separately flagged an elevated `ROLLBACK` count/max-latency and a shared ~57s max-latency spike across unrelated query shapes in the same window, consistent with lock/contention pressure). This mirrors the first session's iteration-2 lesson about implicit pacing.
- `EXPLAIN` on `s2` confirmed `ng_words WHERE livestream_id=?` was a full table scan (`type=ALL`, `possible_keys=NULL`, ~14337 rows) before the fix, and used the new `idx_livestream_id` index type after.
- `EXPLAIN ANALYZE` (both with and without `FORCE INDEX`) on `reservation_slots` with the app's actual realistic parameter range showed the existing full-table-scan behavior is *already optimal* for this app's real query pattern (full scan 2.72ms actual vs forced-index-scan 14.5ms actual) — the SQL Agent's suggestion to force the index was tested and rejected based on this discrepancy between their narrow test range and realistic traffic.

## Change

**Rejected and reverted** (commit `17691ec` reverts the icon_hash portion of `8642c2a`):
- `webapp/go/user_handler.go`: `fillUserResponse` no longer selects `icon_hash`; back to selecting/hashing the full `image` blob (original behavior).
- `webapp/sql/initdb.d/10_schema.sql`: `icons.icon_hash` column removed from the schema definition; dropped live on `s2` (`ALTER TABLE icons DROP COLUMN icon_hash`).

**Accepted** (retained from `8642c2a`, plus a new commit `b1e926d`):
- `webapp/go/livestream_handler.go`: `getLivecommentReportsHandler`'s loop now skips (via `errors.Is(err, sql.ErrNoRows)` + `continue`) a report row whose target livecomment no longer exists, instead of failing the entire request with a 500. Uses an appended slice (`reports := make([]LivecommentReport, 0, len(reportModels))` + `append`) instead of a fixed-size indexed array.
- `webapp/sql/initdb.d/10_schema.sql`: added `CREATE INDEX idx_livestream_id ON ng_words(livestream_id);`. Applied live via `CREATE INDEX` on `s2` before the final deploy.

Files touched across the whole iteration (net): `webapp/go/livestream_handler.go`, `webapp/go/user_handler.go` (net: no change vs. pre-iteration `6be450f`), `webapp/sql/initdb.d/10_schema.sql` (net: `+ng_words(livestream_id)` index only).
