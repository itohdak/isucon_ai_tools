## Hypothesis

The tracked `mysqld.cnf` was effectively stock: live `log_bin=1`, `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`, `innodb_flush_method=fsync` -> roughly 2 fsyncs per commit (154174 `Innodb_os_log_fsyncs` for 83942 `Com_commit`). s2 is the CPU-bound host, so cheaper commits reduce s2's own cost without increasing app-side call volume (the property that made earlier app-side-only optimizations backfire). No replication is used, so the binlog is pure overhead.

## Evidence

- Resource Monitor (iteration 2): s2 idle ~0%, load1 up to 8.2, iowait <=2.5% but `disk_util.nvme0n1` 53-89% during run.
- Live variable dump on s2 (values above). `COMMIT` 3.7ms avg vs ~0.2ms for typical point SELECTs.
- Contest rule check (`/home/itohdak/Downloads/cautionary_note.md`): data written during the load run must still be readable after a server reboot (clean reboot). `flush_log_at_trx_commit=2` writes the redo log to the OS on every commit and only delays fsync ~1s, so data survives a clean reboot; only a power loss/kernel crash could drop ~1s. Regulation-compatible and standard practice.

## Change

`common/etc/mysql/mysql.conf.d/mysqld.cnf` (tracked, deployed to s2 by `deploy_db.sh`): added `disable_log_bin`, `innodb_flush_log_at_trx_commit = 2`, `innodb_flush_method = O_DIRECT`. Slow query log settings (`slow_query_log=1`, `long_query_time=0`) intentionally unchanged (permanent observability). Verified live after deploy: `log_bin=0, flush=2, O_DIRECT, slow_query_log=1, long_query_time=0`.
