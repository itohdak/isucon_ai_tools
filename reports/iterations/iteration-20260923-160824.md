## Hypothesis

The matcher's chair-selection query's correlated `NOT EXISTS(...NOT EXISTS...)` scan (re-checking a chair's full ride/status history on every matching tick) was the SQL Agent's originally-flagged highest-per-call-cost query and a plausible contributor to the DB host's persistent full CPU saturation. Denormalizing "chair is free" into a `chairs.is_free` column, maintained transactionally at the exact two moments the true state changes, should make this a cheap indexed-column check instead.

## Change (implemented per the App Understanding Agent's exact recommendations, approved by the user)

- `webapp/sql/init.sh`: added `chairs.is_free BOOLEAN NOT NULL DEFAULT TRUE` via post-seed `ALTER TABLE` (matching the established pattern for `total_distance`/`latest_latitude` — new columns must not go directly into `1-schema.sql`, see the SQL Agent skill doc), with a one-time backfill `UPDATE` using the exact same `NOT EXISTS` semantics being replaced.
- `webapp/go/models.go`: added `IsFree bool `db:"is_free"`` to the `Chair` struct.
- `webapp/go/internal_handlers.go` (`matchOneRide`): wrapped in an explicit transaction (previously used bare `db.*Context`, which was fine for a single-table write but not for the new two-table write); replaced the `NOT EXISTS` clause with `chairs.is_free = TRUE`; added `UPDATE chairs SET is_free = FALSE ... WHERE id = ?` in the same transaction as the ride assignment.
- `webapp/go/chair_handlers.go` (`chairGetNotification`): added `UPDATE chairs SET is_free = TRUE ...` **gated on `yetSentRideStatus.Status == "COMPLETED"`** inside the existing `if yetSentRideStatus.ID != ""` block — the single most important correctness detail per the App Understanding Agent's analysis, since the existing `chair_sent_at` update fires for every status transition (MATCHING through COMPLETED), not just COMPLETED.
- `appGetNearbyChairs` deliberately left untouched (its own `NOT EXISTS` check answers a different question — display availability — with different semantics, per the agent's explicit recommendation not to conflate the two).

## Verification

- Local build/vet clean. Deployed to `s1`; `/api/initialize` succeeded and backfilled `is_free` correctly (all 500 seeded chairs came back `is_free=1`, consistent with the seed data containing no chairs mid-ride).
- 3 consecutive benchmark runs, all `pass=true`: 12146 (`map[1:2 7:1]`), 12923 (`map[1:2 2:1 7:2]`), 12711 (`map[]`) — scattered minor errors, no `CODE=15`/`CODE=32` recurrence, no new failure signature. Scores are in the same range as immediately before this change.
- **Confirmed the fix worked at the query level**: matching query avg latency dropped from ~51ms to **~14.8ms** (3.5x), max from ~186ms to **~88ms** (2x), verified via a fresh `slp --sort sum-query-time --reverse` full ranking (not narrative) on `s2`'s slow log.
- **However, `s2`'s aggregate CPU remains fully saturated** (`mysqld` avg ~181.7%, idle ~0.1-0.5% during the run) — essentially unchanged from before this fix. Same pattern as the earlier `appGetNearbyChairs` finding: the query was a real, now-fixed inefficiency, but was never the *dominant* aggregate cost at this system's current query-count/throughput level — the top-8-by-`Sum(Query_time)` items (already all indexed) plus sheer per-poll query volume across the whole notification/matching/coordinate path appear to be what's actually saturating 2 vCPUs now.

## Decision

**Keep.** This is a correct, safe, verified improvement (3.5x latency reduction on a genuinely expensive query, careful race-free implementation per a dedicated risk review, backfill correctness confirmed) with no correctness regression across 3 clean runs. It does not, however, create new CPU headroom on `s2` — that ceiling appears to now be a function of aggregate query *volume* across many already-optimized individual queries, not any single remaining expensive query shape.
