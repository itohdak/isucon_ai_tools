## Hypothesis

Almost every hot-path query filters by a foreign-key-style column (`livestream_id`, `user_id`, `tag_id`) but the schema (`webapp/sql/initdb.d/10_schema.sql`) only defines `PRIMARY KEY`s plus 3 unrelated unique/text indexes. Every such lookup is therefore a full table scan. Adding covering secondary indexes on these columns should convert `ALL` scans to `ref`/`range` scans with no behavior change, since these are purely additive schema changes (no new columns, so the `3-initial-data.sql`-positional-INSERT gotcha from the SQL Agent skill doc does not apply — and this app's `init.sh`/`init.sql` only `TRUNCATE`s and reloads data on `/api/initialize`, it does not re-run `CREATE TABLE`, so the schema file at `webapp/sql/initdb.d/10_schema.sql` is provisioned once and the live DB must be altered directly).

## Evidence

- `SHOW CREATE TABLE` on `reactions`, `livecomments`, `livestream_viewers_history`, `livestreams`, `livecomment_reports`, `livestream_tags`, `icons`, `themes`, `reservation_slots`, `ng_words` confirmed no secondary index on any FK-style column.
- Data volumes at baseline: 1186 users, 7578 livestreams, 11303 `livestream_tags` rows, 1203 livecomments, 1191 reactions — small in absolute terms, but every one of these rows gets scanned on every matching lookup, many times per benchmark run.
- SQL Agent's `slp my --sort sum-query-time --reverse` top-15 (bounded to last 50MB of `/var/log/mysql/mysql-slow.log` on s1) showed `SELECT * FROM livestream_tags WHERE livestream_id=N` alone summing to ~67-80s of total query time across the two agent runs (different log windows), by far the largest single contributor; `icons WHERE user_id=N`, `themes WHERE user_id=N`, the tip-sum/reaction-count joins from the stats handlers, and `reservation_slots` range/equality queries rounded out the rest of the top 10.
- `EXPLAIN` confirmed `type=ALL` on all of these, with rows-examined counts matching full table size (e.g. `livestream_tags` scanning ~11k rows per call).

## Change

Applied 10 additive indexes directly on the live `isupipe` database on `s1` via `sudo mysql isupipe -e "ALTER TABLE ... ADD INDEX ..."`, and mirrored them into `webapp/sql/initdb.d/10_schema.sql` (appended a dedicated `CREATE INDEX` block with a comment explaining why, rather than editing each `CREATE TABLE` block, to keep the diff auditable) so the schema file matches the live DB and a from-scratch provision would reproduce it:

- `livestream_tags(livestream_id)`, `livestream_tags(tag_id)`
- `icons(user_id)`
- `themes(user_id)`
- `livecomments(livestream_id)`
- `reactions(livestream_id)`
- `ng_words(user_id, livestream_id)` (composite)
- `reservation_slots(start_at, end_at)` (composite)
- `livestreams(user_id)`
- `livecomment_reports(livestream_id)`
- `livestream_viewers_history(livestream_id)`

No Go application code changed this iteration — pure DB-side change, no deploy/redeploy needed (MySQL data/schema is independent of the Go binary and `/api/initialize` only truncates+reloads data, it does not touch schema).

Files changed: `webapp/sql/initdb.d/10_schema.sql` (committed in the `/home/isucon` repo on s1).

## Verification

Codex verified directly (git status/commit hash on s1, `SHOW CREATE TABLE`/`information_schema.statistics` to confirm indexes landed, `journalctl -u isupipe-go` inspection for new/changed error signatures, 3 full benchmark runs). No sub-agent Verifier used — see table above for why.

- `git log` on s1 confirmed commit `b036a4f` (indexes) was the state benchmarked.
- All 3 runs `pass=true`.
- Investigated the one new-looking error signature (`POST /api/icon` → 500 "Deadlock found when trying to get lock") appearing once per run: occurs mid-run (not at the run's time-boxed cutoff), same signature in all 3 runs — plausibly latent (icon INSERT contention under higher achieved throughput now that other paths are faster) rather than newly introduced by an index specifically on `icons.user_id` (that index doesn't change INSERT locking on the table's own rows). Treated as a candidate for a future iteration (e.g. review the icon POST transaction), not a blocker — occurs at ~1% of icon-post calls and both isupipe.md and cautionary_note.md class isolated "一般エラー" HTTP-code-mismatch messages as benign/non-scoring unless they dominate. The livecomment-report 404s seen in all 3 runs match the memory-noted "already-reported" benign pattern.
- Run 3 additionally showed a burst of DNS (`i/o timeout` on UDP 53 to s1's PowerDNS) resolution failures (103 failures vs 2-3 in the other runs) and 3 request timeouts — not obviously related to the index change (PowerDNS uses a separate `isudns` database, untouched this iteration); flagged as noise to watch in future iterations, did not affect pass/fail.
- End-of-run `context canceled` 500s (moderate/livecomment/reaction/icon/statistics handlers, all at the exact run-cutoff timestamp) are the benchmark client canceling in-flight requests when the time-boxed run ends — expected artifact of the harness, not a regression.

## Next Candidate

`getUserStatisticsHandler` / `getLivestreamStatisticsHandler` (`webapp/go/stats_handler.go`) still issue O(N) round trips (2 queries per user/livestream to build the ranking array — 1186 users / 7578 livestreams at current data volume) even though each individual query is now index-backed instead of a full scan. Rewriting these to a single aggregate `GROUP BY` query per ranking (preserving the exact tie-break: score ascending, then username/ID ascending, rank counted by scanning from the highest score down) should be the next, higher-risk-but-higher-value target — this is App Understanding Agent's #3 finding and was the second- and third-largest SQL total-time contributors in the SQL Agent's ranking (`tip` sum-join and `reaction` count-join queries, ~21s each even pre-index). Also worth a follow-up: `moderateHandler`'s unscoped `SELECT * FROM livecomments` (no `livestream_id` filter) causing multi-second `/moderate` calls, and the nginx log format gap (no `$request_time`) blocking `alp`-based route-latency analysis going forward.
