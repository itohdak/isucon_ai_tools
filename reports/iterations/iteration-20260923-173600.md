# Iteration 2026-09-23 17:36:00

## Agents Used

- App Understanding Agent: reviewed the proposed batch-matching redesign before implementation (matching-strategy change, requires explicit review per `AGENTS.md`). Confirmed the core logic replication was low risk, but flagged that fully uncapping "process the entire backlog" would let per-tick cost scale with backlog size exactly when `CODE=32` risk is highest, and recommended a bounded, incrementally-testable cap plus a `LIMIT` on the ride SELECT. The user chose `maxMatchesPerCall = 10` as the first step (up from 3), per this project's established small-increment discipline (1→3 safe, 1→20 catastrophic, in prior iterations).

## Hypothesis

The user asked whether matching frequency could be increased further, and explicitly authorized moving matching from N per-ride SQL round trips to app-side batch fetch + in-memory assignment if that made a higher throughput safer to implement, including adding a wait-time/urgency cost term later if matching time itself became a bottleneck (deferred to a future Phase 2). Reducing total matching-related query round trips was expected to let a higher per-tick match cap be sustainable within the same DB CPU budget that was previously the ceiling.

## Change

`webapp/go/internal_handlers.go` (commit `00b7246`): replaced the `internalGetMatching` loop of up to 3 independent single-ride transactions (`matchOneRide`, each: 1 SELECT ride + 1 SELECT chair + 2 UPDATE, own commit) with one `matchPendingRides` function that:
- Fetches up to `maxMatchesPerCall` (raised 3 → 10) oldest unmatched rides via one `SELECT ... LIMIT ?` query.
- Fetches all currently free, located, active chairs (joined with `chair_models` for speed) via one unlimited `SELECT` (bounded naturally by fleet size, not backlog size).
- Greedily assigns each ride (oldest first) to its best remaining chair in Go, replicating the original SQL's `(ABS(lat-?)+ABS(lon-?))/speed ASC, chair.updated_at ASC` cost/tie-break exactly via a per-ride stable sort of the remaining candidate pool (avoids float-equality pitfalls from a running-min comparison).
- Applies all resulting ride/chair UPDATEs in a single transaction and commits once.

The `maxMatchesPerCall` cap intentionally stays a hard limit (not "drain the whole backlog") per the App Understanding Agent's review, with the ride SELECT's `LIMIT` tied to the same constant so per-tick cost stays flat even during a backlog episode.

## Verification

- Built clean (`go build ./...`, `go vet ./...`).
- Deployed to `s1`. First benchmark run: **`pass=false`, score 13930, errors dominated by `CODE=1` (158x, "chair coordinate post failed") and no `CODE=32`**. Root cause investigation found `mysqld` on `s2` logging `Error 1040: Too many connections`, with `Max_used_connections` at 152 against a `max_connections` of 151 (MySQL's stock default, never previously configured). The app sets no `db.SetMaxOpenConns`, so mysqld's own limit was the only cap; the batch matcher's single longer-lived transaction (holding locks on up to 10 ride + 10 chair rows at once) was the plausible trigger that tipped an already-thin margin over by one connection.
- **Fix**: raised `max_connections` 151 → 1024 in `/etc/mysql/mysql.conf.d/mysqld.cnf` on `s2` (a standard mysqld config tuning knob, not an instance scale-up) and restarted `mysql.service`. Committed to the tracked config at `isucon14_practice`'s `s2/etc/mysql/mysql.conf.d/mysqld.cnf` (commit `0b78ee2`).
- Re-ran twice after the fix: **`pass=true`, score 21038, errors `map[17:1]`**, then **`pass=true`, score 22818, errors `map[]`** (zero errors). Both are far above the prior best of 13948.

## Decision

**Accepted.** Both the batch-matching redesign and the `max_connections` fix are kept. The connection-limit failure was an infrastructure headroom issue exposed by the change, not a defect in the matching logic itself — the matching logic's own correctness (selection formula, tie-break, freeness check, atomicity) was never in question across any of the three runs.

**Lesson recorded**: a hard resource limit that was never hit before (MySQL's stock `max_connections=151`) can become the binding constraint once a change increases how long a transaction holds its connection/locks, even if that same change reduces total round trips. Any future change that lengthens per-transaction hold time (larger batches, more work per commit) should be checked against `Max_used_connections` headroom, not just query-count or CPU metrics.
