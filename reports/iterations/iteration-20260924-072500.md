## Hypothesis

Iteration 1 showed that making *search* faster makes the score worse (bench scenario mix), and iteration 2 showed that cutting s1 CPU helps (viewer completions 975 -> 1036). `viewer` completions produce the tips, and the viewer's calls are `POST/GET livecomment`, `POST/GET reaction`. Cut their DB round trips (per POST: BEGIN, SELECT livestream, SELECT ng_words, N x COUNT, INSERT, SELECT livestream, 2 tag queries, COMMIT = ~10 -> 2) while leaving search and the other list handlers untouched.

## Change (commit ffac697)

- `livestream_handler.go`: `getLivestreamModelCached` + `fillLivestreamResponseCached` (livestream rows and tag lists are insert-only, committed atomically, unreachable before commit; only successful reads cached; owner/icon hash still resolved per call; `initialize` clears via `clearUserCaches`). `fillLivestreamResponse` keeps its behaviour through the extracted `loadLivestreamTags`.
- `livecomment_handler.go` `postLivecommentHandler`: no transaction; one `SELECT COUNT(*) FROM ng_words WHERE user_id=? AND livestream_id=? AND ? LIKE CONCAT('%', word COLLATE utf8mb4_general_ci, '%')` instead of a SELECT plus a COUNT per word (verified on s2 against the original literal-vs-literal form: case-insensitive match, `_` wildcard and Japanese words behave identically); INSERT autocommit; cached fill.
- `reaction_handler.go` `postReactionHandler`: no transaction (livestream resolved before the INSERT so a missing livestream still returns 500 without leaving a row); `getLivecommentsHandler`/`getReactionsHandler` use the caches.
- Search (`GET /api/livestream/search`), `GET /api/livestream`, `GET /api/user/:u/livestream` keep hitting MySQL on purpose.
