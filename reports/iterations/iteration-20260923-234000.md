# Iteration 9 — ISUCON13 (ISUPipe): Fix shared-livestream N+1 in getLivecommentsHandler/getReactionsHandler (biggest single win this session)

## Agents Used

No new sub-agent dispatch — this iteration was found by Codex directly while investigating the next candidate after iteration 8, by reading `reaction_handler.go` and `livecomment_handler.go` in light of iteration 5's Profiler Agent data (which had ranked `GET livecomment` and `GET reaction` as the #1 and #2 highest-*total-time* routes: 606,172ms and 577,184ms summed respectively, 2056 and 2158 calls). Sub-agents were not used because: this was a direct code-reading exercise following up on already-dispatched Profiler data, and the fix (once the pattern was spotted) was immediately obvious and narrow in scope, not requiring fresh analysis.

## Hypothesis

`getLivecommentsHandler` and `getReactionsHandler` both list comments/reactions for a single livestream (`WHERE livestream_id = ?`, from the path parameter) and then, for **every row** in the result, call `fillLivecommentResponse`/`fillReactionResponse` — which each independently re-fetch and re-fill the **entire Livestream object** (owner user lookup, icon hash computation via `fillUserResponse`, and — since iteration 8 — a batched but still per-call tags query) from `livecommentModel.LivestreamID`/`reactionModel.LivestreamID`. Since every row in either handler's result set shares the exact same `livestream_id` (the query is scoped to it), this livestream data is **identical across every row** — re-fetching it once per row is a pure N+1 with zero variation in the result. Fetching and filling the livestream **once per HTTP call**, then reusing that single `Livestream` struct for every row, should produce byte-identical output while cutting the dominant per-row cost entirely.

## Evidence

- Iteration 5's Profiler Agent ranking (journalctl-derived, `a605b23` window): `GET livecomment` (2056 calls, 294.8ms avg, 606,172ms sum — #1 by total time) and `GET reaction` (2158 calls, 267.5ms avg, 577,184ms sum — #2 by total time) were the two largest total-time contributors in the entire app, together summing to more total time than every other route combined.
- Direct code read confirmed the exact mechanism: `fillLivecommentResponse`/`fillReactionResponse` each independently call `tx.GetContext(... "SELECT * FROM livestreams WHERE id = ?" ...)` then `fillLivestreamResponse(...)` (owner + icon + tags) — with no sharing across calls within the same handler invocation, despite all rows sharing one `livestream_id`.
- Call-site audit (`grep -rn 'fillLivecommentResponse(\|fillReactionResponse('`) confirmed exactly one list-loop call site each (the ones fixed here) plus single-item call sites in `postLivecommentHandler`/`postReactionHandler`/`fillLivecommentReportResponse`, which are legitimately single-row and were left untouched to avoid any behavior change there.

## Change

Added `fillLivecommentResponseWithLivestream(ctx, tx, livecommentModel, livestream Livestream)` and `fillReactionResponseWithLivestream(ctx, tx, reactionModel, livestream Livestream)` — each identical to the original function except taking an already-filled `Livestream` instead of re-fetching one. Refactored the original `fillLivecommentResponse`/`fillReactionResponse` to fetch+fill the livestream once and delegate to the new `...WithLivestream` variant, so their behavior for existing single-item call sites is provably unchanged (same two queries, same order, same output). In `getLivecommentsHandler`/`getReactionsHandler`, replaced the per-row `fillLivecommentResponse`/`fillReactionResponse` calls with: fetch+fill the livestream **once**, guarded by `if len(models) > 0` (so a livestream with zero comments/reactions triggers zero extra queries and cannot turn an invalid `livestream_id` into a new not-found error — preserves the original empty-list behavior exactly, since the query is only reached when at least one row already proves the livestream_id is valid), then loop calling the `...WithLivestream` variant with the shared value. `go build`/`go vet`/`gofmt -l` clean.

Files changed: `webapp/go/livecomment_handler.go`, `webapp/go/reaction_handler.go`.
