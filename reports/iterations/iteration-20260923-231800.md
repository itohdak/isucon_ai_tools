# Iteration 6 — ISUCON13 (ISUPipe): PowerDNS index + persistent slow-query-log (BOTH REJECTED — reverted)

## Agents Used

Reused iteration 5's SQL Agent and Profiler Agent findings (no new dispatch — both candidates were already fully specified: "PowerDNS `isudns.records` missing `(name,type)` index" and "MySQL slow-query logging silently reset to OFF after a `mysqld` restart"). Sub-agents were not used because: both hypotheses were already evidenced and scoped by iteration 5's dispatch; this iteration was pure implementation + verification, and the verification itself (a multi-step A/B isolating two independent regressions) needed tight, immediate iteration between benchmark runs that a delegated Verifier Agent would have slowed down.

## Hypothesis

1. `isudns.records` (PowerDNS's backend table, separate `isudns` schema on the same MySQL instance) has no index on `name`/`(name,type)`, forcing a full table scan on every DNS lookup — SQL Agent measured ~19.3s combined query time in one sample. Adding the standard PowerDNS `nametype_index` should be a safe, low-risk win (standard recommended PowerDNS schema addition, doesn't touch the isupipe app DB).
2. MySQL slow-query logging was silently reset to OFF by iteration 4's `mysqld` restart, because the **tracked** `common/etc/mysql/mysql.conf.d/mysqld.cnf` (which `deploy.sh` copies over the live config on every deploy) has `slow_query_log`/`long_query_time` commented out — a prior session's fix was apparently only ever a live `SET`/file edit that was never committed, so it silently reverted on the next deploy. Persisting `slow_query_log=1`/`long_query_time=0` in the tracked file should restore reliable SQL Agent analysis for future iterations without needing to remember to re-enable it after every deploy.

## Evidence (before change)

- `SHOW CREATE TABLE records` on `isudns` confirmed only `PRIMARY`, `domain_id`, and `ordername` indexes — nothing on `name` or `type`. `EXPLAIN` on the hot query (`SELECT ... FROM records WHERE disabled=? AND name=? AND domain_id=?`) showed `type: ALL`.
- `/etc/mysql/mysql.conf.d/mysqld.cnf` (live) and `common/etc/mysql/mysql.conf.d/mysqld.cnf` (git-tracked) both had `slow_query_log`/`slow_query_log_file`/`long_query_time` commented out — config-file default is OFF, and `deploy.sh` overwrites the live file with the tracked one, then unconditionally restarts `mysqld`, on every deploy.

## Change (implemented, then both reverted)

1. `CREATE INDEX nametype_index ON isudns.records(name, type);` — applied directly to the live `isudns` database (PowerDNS's own schema, not tracked in the app's git repo, so no source file to mirror).
2. Uncommented `slow_query_log = 1` / `slow_query_log_file = /var/log/mysql/mysql-slow.log` / `long_query_time = 0` in both the live `/etc/mysql/mysql.conf.d/mysqld.cnf` and the tracked `common/etc/mysql/mysql.conf.d/mysqld.cnf`, committed as `8e56614`, redeployed to confirm it survives a full `deploy.sh` cycle (it did).

## Verification and what was actually found (the interesting part)

Codex verified directly with a step-by-step A/B, since the first combined-change benchmark run looked like a clear regression and needed isolating:

| State | Score | DNSAttacker並列数 (bench-internal DNS-attack concurrency) | 名前解決成功数 (DNS resolutions succeeded) |
| --- | --- | --- | --- |
| Both changes (index ON, log ON) — run 1 | 8770 | 3 | 4643 |
| Both changes (index ON, log ON) — run 2 | 7912 | 3 | 4220 |
| Index ON, log OFF | 10211 | 3 | 5836 |
| Index OFF, log OFF (reverted) — run 1 | 10676 | 2 | 1578 |
| Index OFF, log OFF (reverted) — run 2 | 11356 | 2 | 1580 |
| Index OFF, log ON (isolating log alone) | 8707 | 2 | 1678 |
| Final reverted state, redeploy-confirmed | 11903 | 2 | 1491 |

Two distinct, independently-confirmed regression mechanisms, both traced to `s1`'s hard CPU constraint (2 vCPUs, confirmed CPU-saturated by iteration 5's Resource Monitor Agent):

1. **The PowerDNS index change back-fires because the benchmark's own adaptive load control reacts to it.** With the index applied, `DNSAttacker並列数` (the bench's internal DNS-attack scenario concurrency) rose from its steady value of 2 to 3, and successful DNS resolutions roughly tripled (1500→4200-5800) — the benchmark appears to ramp up adversarial DNS load once it observes the DNS server coping well, which then competes for the same 2 vCPUs as the app/mysqld and measurably reduces the higher-value app traffic that actually drives score. This is the same class of lesson as iteration 2 (fixing one path can expose or amplify contention elsewhere in a resource-constrained, shared system) but via the benchmark's adaptive behavior rather than an app-side connection pool.
2. **`long_query_time=0` (log every query) has a real, substantial CPU/IO cost on this constrained host.** Isolated with `DNSAttacker並列数` pinned at 2 (index reverted) so it wasn't a confound: log ON scored 8707 vs log OFF's 10676/11356 — a clear, reproducible ~20-25% cost from logging every single query, on top of everything else already competing for the same 2 vCPUs.

Both changes reverted: index dropped live (`DROP INDEX nametype_index ON records`), `slow_query_log` set back to OFF live (`SET GLOBAL slow_query_log = 0`), and the tracked `mysqld.cnf` change reverted via `git revert --no-edit 8e56614` (commit `7ea20c2`) so a future deploy doesn't silently reintroduce the logging overhead. Redeployed and confirmed the live state matches (`slow_query_log OFF`, no `nametype_index`), then re-benchmarked: **11903**, consistent with iteration 5's average — confirms the revert is clean.

## Benchmark Result

Both changes **rejected and reverted**. No net change to the accepted baseline: still iteration 5's `efae626` (avg 12248.3), now also carrying revert commit `7ea20c2` (a no-op for the app, restores `mysqld.cnf` to its pre-iteration-6 content).

## Next Candidate

**Durable lesson for future SQL Agent dispatches on this environment:** do not leave `slow_query_log=1`/`long_query_time=0` enabled during a scored/verification benchmark run — it costs ~20-25% throughput on this CPU-constrained 2-vCPU host. Instead, temporarily enable it (`SET GLOBAL slow_query_log = 1; SET GLOBAL long_query_time = 0;`) immediately before a dedicated analysis-only benchmark run, collect the slow log, then disable it again (`SET GLOBAL slow_query_log = 0;`) before the next benchmark run whose score is meant to count. Recorded in `docs/skills/sql-agent.md` for future sessions (see below).

**Do not pursue the PowerDNS index further** under the current benchmark's adaptive-load behavior — it's a rare case of "this makes the component faster but the benchmark punishes you for it" that's now well-evidenced and shouldn't be re-attempted without new evidence that the adaptive DNS-attacker concurrency is itself capped/bounded elsewhere.
