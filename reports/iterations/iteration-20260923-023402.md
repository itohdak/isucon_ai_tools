## User Finding

The user noticed a specific query — the "latest chair location" JOIN used by `GET /api/app/nearby-chairs` — and asked whether the SQL Agent had addressed it, since it looked like both a high per-call and high cumulative latency consumer. It had **not** been explicitly covered by the prior SQL Agent report (`reports/iterations/iteration-20260923-012833.md`), which was scoped to *cumulative CPU-cost ranking* and flagged `internalGetMatching`'s structurally-similar query instead (higher per-call cost at the time, ~267 calls/2min vs. this endpoint's ~69 calls/2min in the original Profiler Agent baseline much earlier in the session).

## Investigation

- Confirmed via `EXPLAIN`/`EXPLAIN ANALYZE` on `s3` that the query's plan is actually efficient (a loose index scan for the `MAX(created_at)`-per-chair group-by, "Using index for group-by") — not a bad plan, but it **fully recomputes "latest location for every active chair" from scratch on every single call**.
- Checked the slow log for actual call latency: 32 calls averaging **132ms**, max **429ms** — a real outlier compared to nearly every other query measured this session (sub-millisecond to a few ms).
- `internalGetMatching`'s chair-selection query uses the exact same "latest location per chair" derived-table pattern, so it does the identical recomputation on every matching tick too — this is real, avoidable duplicated work layered on top of `s3` already being CPU-saturated (from the prior DB-tuning iteration).

## Change (approved by user, since it touches `internalGetMatching`)

Denormalized "latest chair location" onto the `chairs` row, following the same pattern already proven for `chairs.total_distance`:

- `chairs.latest_latitude`/`latest_longitude` (nullable, added via `ALTER TABLE` in `init.sh` **after** the seed data load — adding them directly to `1-schema.sql`'s `CREATE TABLE` broke `3-initial-data.sql.gz`'s positional `INSERT INTO chairs VALUES (...)`, which matches the original 8-column shape; caught this immediately via `/api/initialize` failing with "Column count doesn't match value count," reverted the schema-file approach, and followed the established post-seed-`ALTER` pattern instead, backfilling from any pre-seeded `chair_locations` history in the same `UPDATE`).
- `chairPostCoordinate` now sets `latest_latitude`/`latest_longitude` in the same `UPDATE chairs ...` statement it already uses for `total_distance` — no extra query.
- `appGetNearbyChairs` and `internalGetMatching`'s `matchOneRide` both read `chairs.latest_latitude`/`latest_longitude` directly instead of joining through the per-call derived table. **Selection logic unchanged** (freeness check, distance/speed ordering, `chairs.updated_at` tie-break) — only how the location value is obtained changes. Added an explicit `latest_latitude IS NOT NULL` filter to preserve the previous `INNER JOIN`'s implicit exclusion of chairs with no location history (important for `internalGetMatching`, since MySQL sorts `NULL` first in `ASC` order — without this filter a never-located chair could wrongly appear "closest").
- Commits: `7b6a13f` (initial denormalization) and `1099e7b` (fix: move new columns from `1-schema.sql` to a post-seed `ALTER` in `init.sh`, matching the `total_distance` precedent).

## Verification

- 3 benchmark runs, all `pass=true`: 12746 (`map[1:4 17:1 21:1]`), 12406 (`map[1:9 3:1 7:3 8:1 17:1 21:9 25:1]`), 12741 (`map[]`) — scattered minor errors, none causing failure, in the same noisy range as the pre-fix `maxMatchesPerCall=3` baseline.
- **Confirmed the fix worked as intended at the query level**: `appGetNearbyChairs`'s query latency dropped from avg 132ms/max 429ms to **avg 27ms/max 76ms — roughly a 5x reduction**. `internalGetMatching`'s chair-selection query also improved (max latency down from ~280ms to ~186ms), though less dramatically since it still carries the separate correlated-subquery freeness check (SQL Agent's finding #3) that this change didn't touch.
- **However, `s3`'s overall CPU is still fully saturated** (idle ~0.1-1.2% during the benchmark window, `mysqld` averaging ~180.6% — essentially unchanged from before this fix). This confirms the "latest location" recomputation, while a real and now-fixed inefficiency, was never the *dominant* cumulative CPU cost — its high observed latency in the slow log was largely a symptom of queueing behind other CPU-bound work on an already-saturated host, not a cause of that saturation itself.

## Decision

**Keep.** This is a correct, safe, verified improvement (5x latency reduction on a genuinely wasteful repeated computation, no behavior change, backfill correctness confirmed via `COUNT(latest_latitude)` after `/api/initialize`) — it reduces tail-latency risk on `/api/app/nearby-chairs` and modestly helps the matching query, independent of whether it moves the overall CPU-saturation needle. It does **not**, however, resolve `s3`'s CPU saturation or create headroom for a larger `maxMatchesPerCall` — that still requires addressing the SQL Agent's finding #3 (the matcher's correlated `NOT EXISTS` chair-freeness check, which scales with active-chair count and is unrelated to the location lookup this iteration fixed).
