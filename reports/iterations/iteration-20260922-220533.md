## Hypothesis / Root Cause Investigation

The previous iteration (`reports/iterations/iteration-20260922-211313.md`) rejected a `FOR SHARE`-removal change after it produced one `CODE=15` benchmark failure ("a chair received a new ride's notification before receiving its current ride's completion notification"), with only a working theory about the cause. The user asked for the actual root cause.

Investigation steps and findings:

1. Read `internal_handlers.go` (`internalGetMatching`): it does `SELECT` the oldest unassigned ride, `SELECT` the best free chair, then `UPDATE rides SET chair_id = ?` — all as separate, non-transactional, autocommit statements.
2. Checked `isuride-matcher.service`'s definition: `while true; do curl -s .../api/internal/matching; sleep $ISUCON_MATCHING_INTERVAL; done` — a single sequential shell loop (`ISUCON_MATCHING_INTERVAL=0.5`), confirmed as the *only* caller of this endpoint (`grep` across systemd units). `ps aux` showed exactly one such process; no duplicate/leaked matcher process.
3. Pulled the failed run's own pprotein httplog (`dlltzj4u088x-httplog.log`, identified as the shortest/failed run by file size) and confirmed all `/api/internal/matching` requests were sequential with sub-40ms `apptime` and no overlapping timestamps — ruling out concurrent/overlapping matcher calls as the mechanism.
4. Re-examined the actual bug: `chairGetNotification` selects the ride to report on via `SELECT * FROM rides WHERE chair_id = ? ORDER BY updated_at DESC LIMIT 1` — i.e. "whichever ride was most recently touched" for that chair. `rides.updated_at` has `ON UPDATE CURRENT_TIMESTAMP(6)`, so it bumps whenever `chair_id` is written, including by `internalGetMatching`'s `UPDATE`.
5. `appPostRides` inserts an initial `MATCHING` ride_statuses row (unsent) at ride creation, before any chair is assigned.

**Root cause (deterministic, not a race):** `internalGetMatching` only checks whether a chair's previous ride has a `COMPLETED` ride_statuses row *inserted* — not whether the chair has actually been notified of it (`chair_sent_at`). Sequence:
1. Chair X is on ride A (ARRIVED). User submits evaluation → `appPostRideEvaluatation` inserts `COMPLETED` for ride A (committed).
2. Before chair X's *own* next poll observes that `COMPLETED` row, `internalGetMatching` runs (every ≤0.5s) and sees "no assigned ride without COMPLETED" for chair X → assigns a brand-new ride B to chair X.
3. Ride B's `updated_at` (just written) is now newer than ride A's, so chair X's *next* `chairGetNotification` poll returns ride B instead of ride A.
4. Ride A's already-inserted, still-unsent `COMPLETED` status can now never be selected again for chair X (the query only ever looks at the single most-recently-updated ride) — it is silently and permanently stranded, violating "deliver every transition at least once."
5. The chair receives ride B's `MATCHING` notification without ever having received ride A's `COMPLETED` notification → exactly the bench's `CODE=15` message.

This is a **pre-existing latent correctness bug**, not something introduced by the `FOR SHARE` removal. It is probabilistic only in the sense that it requires the matcher to reassign a chair inside the narrow window between "COMPLETED recorded" and "chair's own poll observes COMPLETED" — a window that shrinks or grows with overall system timing/throughput. Any future latency improvement can shift the odds of hitting it, which is consistent with it appearing only once in the ~8 runs conducted today, correlated with (but not necessarily caused specifically by) the `FOR SHARE` removal's throughput change.

## Change (approved by user, since it changes matching strategy)

- `webapp/go/internal_handlers.go`: `internalGetMatching`'s "chair is free" check now additionally requires `completed_statuses.chair_sent_at IS NOT NULL` on the `COMPLETED` row, not just its existence. A chair is no longer eligible for a new ride until it has actually polled and received the completion notification for its previous one. Added an explanatory comment since the invariant is non-obvious.
- Commit: `9179ded close CODE=15 race: require notification-delivered COMPLETED before rematching chair`.
