## Verification

- Deployed to `s1`. **Benchmark run: `pass=false`, score 11749, errors `map[1:161 2:8 3:6 7:2 8:5 13:1 17:6 19:1 21:5 25:6 30:2]`** — the same "too many errors" overload signature seen with the earlier rejected 20x attempt, this time triggered by a much smaller step (3→5).
- Queried Netdata for the exact failed-run window (2026-09-22T15:55:13–15:56:13 UTC) for both hosts:
  - **`s3` (db host)**: CPU idle collapsed to ~1-1.6% for the sustained middle portion of the run (`user` alone at 66-68%, `system` ~18%, `softirq` ~10%). Load average (`load1`) climbed from 0.4 to a peak of **18.04** on a 2-vCPU host — roughly 9x overloaded.
  - **`s1` (app host)**: CPU idle stayed at 41-95% throughout the same window — `s1` was *not* the constraint this time.
- This is direct, conclusive evidence (not just inference) that `s3`'s MySQL CPU capacity, not `s1`, is what broke at batch size 5. This matches the previous iteration's `pidstat` finding that `s3`'s `mysqld` was already averaging ~169% CPU (out of a 200% ceiling) at batch size 3 — very little headroom remained.

## Decision

**Rejected, reverted immediately.** `git revert 9b949ef` (commit `38b02eb`), redeployed, re-verified: `pass=true`, score `13191`, errors `map[26:1]` (the pre-existing, unrelated owner-distance-freshness warning). System confirmed back to the known-stable `maxMatchesPerCall = 3` state.

`maxMatchesPerCall = 3` is the current safe ceiling given `s3`'s present CPU capacity (a `c5.large`, 2 vCPUs). Increasing it further without first addressing `s3`'s own CPU cost (or giving it more CPU) will very likely reproduce this same overload.

## Next Candidate

- Now that `s3`'s CPU is the confirmed bottleneck at `maxMatchesPerCall = 3`, further matching-throughput gains require either:
  1. Reducing MySQL's own CPU cost on `s3` (query/index optimization — the SQL Agent's earlier analysis loop would be a good fit here, now pointed at `s3`'s slow log instead of `s1`'s), or
  2. Giving `s3` more CPU (a larger instance type), which is a bigger, costed infrastructure change and should go through the same explicit-approval process as the original split.
- Do not increase `maxMatchesPerCall` again without first confirming `s3` has real headroom (via Netdata, as done here) — the 3→5 step alone was enough to fully saturate it.
- Consider whether `s3`'s `mysqld` config (e.g. `key_buffer_size`, connection pool settings per `docs/mysql-operations-tips.md`) has any low-risk tuning headroom before resorting to a bigger instance.
