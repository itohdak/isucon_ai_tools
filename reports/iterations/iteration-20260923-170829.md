## Agents Used

## Hypothesis

The user proposed testing a bigger increase to the idle notification `retry_after_ms` (100 → 300) than the conservative first step, reasoning (and Codex agreed at the time) that raising a client poll-wait hint should only ever *reduce* server load, never risk an overload — unlike a server-side rate limit such as `maxMatchesPerCall`.

## Change

`webapp/go/chair_handlers.go`: `notificationRetryAfterMsIdle` 100 → 300 (pending-case `30` unchanged). Commit `2959d57`.

## Verification

- Deployed to `s1`. **Benchmark run: `pass=false`, score 14410 (highest raw score seen, but invalid), errors `map[17:5 32:4]`** — `CODE=32` ("ride not matched for a long time") occurred 4 times, a real failure.

## Root Cause (working theory, not fully confirmed)

The premise that "a longer idle `retry_after_ms` can only reduce load, never cause an overload" was **incomplete**. It's true for the *server's* database load, but ignores that the benchmark's simulated chair client may couple its notification-poll cadence to *other* client-side actions (most plausibly, how often it posts its coordinate via `POST /api/chair/coordinate`). `matchOneRide`'s candidate query requires `chairs.latest_latitude IS NOT NULL`, which is only populated once a chair has posted at least one coordinate — if a newly-registered chair's first notification response ("no ride yet", the idle case) also gates or paces its first coordinate post, a much longer idle wait (300ms vs 100ms) could measurably delay that chair becoming matchable at all, producing exactly the observed `CODE=32` pattern. This was not verified by reading the benchmark's own client source (not available), only inferred from the failure signature and the mechanism connecting `latest_latitude` to matchability.

## Decision

**Rejected, reverted immediately** (single failing run was sufficient — this session's established policy treats a clear failure signature as not needing repeat confirmation, per `docs/skills/verifier-agent.md`). Reverted `notificationRetryAfterMsIdle` to `100` (commit `cb8f6f5`), redeployed, and re-confirmed: `pass=true`, score **13948** (a new high, and higher than any of the three 100ms runs from the previous iteration — consistent with normal run-to-run noise, not evidence that 100ms itself improved).

**Lesson recorded in the code comment and here**: do not assume a client-facing timing parameter is safe to increase just because the *server-side* resource-consumption argument is monotonic. Client behavior can be coupled to that parameter in ways invisible from the server code alone. Any future attempt to raise `notificationRetryAfterMsIdle` beyond 100 should be tested as its own single small step and watched specifically for `CODE=32`, not assumed safe by extrapolation from this incident's specific failure mode alone.
