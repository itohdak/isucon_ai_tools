## Hypothesis

`chairGetNotification` (the highest-volume endpoint) took a `FOR SHARE` row lock on `users` on every poll, while the equivalent chair lookups elsewhere used a plain `SELECT`. Since `users.firstname`/`lastname` are write-once and nothing else locks that row, the lock looked like pure unnecessary InnoDB bookkeeping overhead on the hottest path.

## Evidence

- `grep -n "FOR SHARE\|FOR UPDATE" *.go` showed exactly one `FOR SHARE` in the whole codebase, on `chair_handlers.go:254`, and no other query ever locks or writes `users` rows post-creation.
- The equivalent chair-lookup queries in `app_handlers.go` (lines 243, 732) use plain `SELECT`, confirming the `FOR SHARE` here was asymmetric/likely vestigial rather than load-bearing.

## Change

- `webapp/go/chair_handlers.go`: removed `FOR SHARE` from the `users` lookup in `chairGetNotification`. Commit `65d9b68 remove unnecessary FOR SHARE lock on immutable user read`.

## Verification

- Local build/vet: clean.
- Deployed to `s1`, all services active.
- **Benchmark run 1**: `pass=true`, score `5185`, errors `map[]`.
- **Benchmark run 2**: `pass=true`, score `5133`, errors `map[]`.
- **Benchmark run 3**: `pass=false`, score `971`, error `CODE=15`: "椅子がライドの完了通知を受け取る前に、別の新しいライドの通知を受け取りました" (a chair received a new ride's notification before receiving its current ride's completion notification) — a real correctness violation of the notification/matching invariant, not a score-only issue.
- To rule out a pre-existing/unrelated flaky bug, immediately rolled the app host back to the previous commit (`9feff84`, detached HEAD) and re-ran the benchmark twice: `pass=true` / score `5183` / `map[]`, then `pass=true` / score `5324` / `map[]`. Both clean.
- This asymmetry (2/2 clean on `9feff84` vs. a hard failure by the 3rd run on `65d9b68`) is not large-sample-conclusive, but combined with the fact that the change touches the exact notification transaction the project's own risk notes flag as invariant-sensitive, the safe call is to treat it as causally implicated rather than assume coincidence.
- **Decision: reject and roll back.** Created `git revert 65d9b68` (commit `085609b`) rather than force-editing history, pushed, and fast-forwarded the app host back onto `main`. Redeployed and re-verified once more: `pass=true`, score `5215`, errors `map[]`.

## Working Theory (Unconfirmed)

The `FOR SHARE` was probably never required for *its own* correctness (nothing else locks or writes that row), but removing it made `chairGetNotification` faster, which likely increased chair polling/notification throughput enough to raise the odds of hitting a **pre-existing, latency-sensitive race** elsewhere (most likely in matching/ride-assignment, since the error is specifically about a chair being handed a new ride before its current one completed). This is a hypothesis, not a confirmed root cause — it was not tracked down further in this iteration because the immediate priority was to stop shipping a run that can fail the benchmark outright.
