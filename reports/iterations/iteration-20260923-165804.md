## Hypothesis

SQL-level query optimization on the DB host (`s2`) has hit diminishing returns: the top-8 queries by `Sum(Query_time)` were already indexed, and the two highest per-call-cost outliers (nearby-chairs, matcher chair-selection) were both fixed in prior iterations — yet aggregate CPU stayed fully saturated. The remaining lever, per `docs/isucon14-improvement-approach.md`'s original priority list, is reducing query *count*, not just per-query cost. `GET /api/{app,chair}/notification` returns a fixed `retry_after_ms=30` regardless of whether there's anything to report, so idle clients poll exactly as often as ones mid-transition.

## Change (confirmed with the user, including a mid-discussion correction of which direction actually reduces load)

`webapp/go/chair_handlers.go` / `app_handlers.go`: when a notification poll finds a pending (not-yet-sent) status transition, keep `retry_after_ms=30` (drain the queue promptly). When the client is fully caught up (nothing pending), return `retry_after_ms=100` instead — a modest first step, not a large jump, given uncertainty about how added notification latency trades off against ride throughput/score. Commit `20e771a`.

## Verification

- Local build/vet clean. Deployed to `s1`.
- 3 consecutive benchmark runs, all `pass=true`: **13146** (`map[1:7 7:3 8:2 17:2 30:3]`), **13474** (`map[1:5 3:3 7:5 17:1 19:1 30:1]`), **13490** (`map[1:12 8:1 17:3 19:1 30:1]`) — all new highs for this environment, no `CODE=15`/`CODE=32` recurrence, error counts scattered/minor.
- `s2`'s aggregate CPU is essentially unchanged (`mysqld` avg ~171.7%, idle ~1-3% during the run) — this change did not free CPU headroom, but the score improved anyway (~5-10% over the pre-change 12000-13000 range), implying the same CPU budget is now doing more useful work per cycle rather than spending as much of it on "nothing changed" poll responses.

## Decision

**Keep.** Clear, reproducible score improvement across 3 runs with no correctness regression. The idle `retry_after_ms` value (100ms) was deliberately conservative; a further increase could be tried as a separate, small next step and re-measured, but should not be assumed safe without testing given the score's sensitivity to notification latency.
