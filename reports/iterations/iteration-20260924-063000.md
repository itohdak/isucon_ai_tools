## Hypothesis

`search?limit=50` runs ~100 tag queries per call (2 per livestream). Fetch tags for the whole list with one `livestream_tags ... IN (...) ORDER BY id` and one `tags IN (...)` query. This removes ~285k queries per run from s2 and ~250k round trips (Syscall6) from s1, the constrained host.

## Why it lost (mechanism, same as iteration 10 of the second session)

Making search fast makes the bench run about 2.5x more `aggressive-streamer-moderate` / `viewer-spam` / `streamer-moderate` scenario iterations and about 10% fewer `viewer` completions (`viewer` is what generates tips = the score). The extra spam/moderation traffic costs the hosts (DELETEs, NG-word checks) and yields no tips. This is now confirmed twice by opposite implementations (a cache in the second session, a batch query now), so the cause is "search latency", not the implementation. Do not speed up `GET /api/livestream/search` (or anything that feeds those scenarios) without a compensating benefit; observe the scenario counts on every run.
