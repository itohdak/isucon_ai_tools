# Iteration 3 — ISUCON13 (ISUPipe): Raise DB connection pool (SetMaxOpenConns/SetMaxIdleConns 10→50)

## Agents Used

No new sub-agent dispatch — hypothesis came directly out of iteration 2's A/B investigation (a Codex-driven root-cause analysis of the stats-handler regression), which is a valid case for a tightly-scoped, evidence-backed direct action per AGENTS.md ("Skipping sub-agents is allowed... when the next action is urgent or tightly coupled" / already-identified "Next Candidate" from the prior report). Sub-agents were not used because: this was a single-line, low-risk, already-well-evidenced config change following directly from iteration 2's own benchmark data (the 10-connection ceiling theory), not a new area needing fresh analysis.

## Hypothesis

`webapp/go/main.go`'s `connectDB()` calls `db.SetMaxOpenConns(10)` with no `SetMaxIdleConns`. `SHOW GLOBAL VARIABLES LIKE 'max_connections'` on s1's MySQL shows a ceiling of 151, with `Max_used_connections` at only 18 historically — MySQL itself has far more headroom than the app's Go-side pool allows it to use. Iteration 2's A/B (stats-handler fix alone caused a ~26% score *regression* despite being strictly less total DB work) pointed at this 10-connection cap as an implicit throttle: raising it should let the app actually exploit the index/lower-latency gains from iteration 1 (and set up iteration 2's fix to work once retried).

## Evidence

- `SHOW GLOBAL VARIABLES LIKE 'max_connections'` → 151. `SHOW STATUS LIKE 'Max_used_connections'` → 18 (well under both the old cap of 10 — meaning the pool was very likely saturated/queueing under load — and the new MySQL-side ceiling).
- Resource Monitor Agent's iteration-1 finding: s1 has ample CPU/memory headroom (87%+ idle), so raising concurrency has room to help rather than immediately hitting a hardware ceiling.
- This is a pure application-level Go config change (connection pool size), not an instance/hardware resource change — stays within the Resource And Split Policy (only instance type/size scale-ups are prohibited; using existing DB connection headroom more fully is exactly the kind of "use existing resources more efficiently" optimization the policy explicitly allows).

## Change

`webapp/go/main.go`: `db.SetMaxOpenConns(10)` → `db.SetMaxOpenConns(50)` + added `db.SetMaxIdleConns(50)` (avoids connection churn/reconnect overhead as the pool is used more fully). 50 was chosen as a conservative 5x increase leaving headroom below MySQL's 151 cap for pprotein-agent, admin/monitoring connections, and PowerDNS's separate `isudns` connections on the same MySQL instance — not tuned to a precise optimum this iteration.

Files changed: `webapp/go/main.go`.
