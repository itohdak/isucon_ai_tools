## Hypothesis

`getChairStats` (called from `appGetNotification` on every `/api/app/notification` poll when the ride has a chair) ran one unbounded `SELECT * FROM rides WHERE chair_id = ? ORDER BY updated_at DESC` query, then one more unbounded `SELECT * FROM ride_statuses WHERE ride_id = ? ORDER BY created_at` query per row returned — a classic N+1 that grows with the chair's accumulated ride history and fires on every ~30ms poll. All three analysis agents converged on this as the top actionable finding.

## Evidence

- Profiler: `/api/chair/notification` (23,402 req, 981.5s total) and `/api/app/notification` (16,249 req, 949.3s total) dominate total API time by volume; individual calls average 42-58ms, so the endpoints are not slow per-call but are called constantly.
- SQL Agent: the two `getChairStats` queries appeared 59,408 and 12,974 times respectively in a sampled slow-log window, summing to roughly 66-72s of DB time via sheer round-trip count, separate from (and not shown in) the profiler's single-run `slp` ranking because the profiler's capture window and the SQL agent's live-log sample covered different spans.
- App Understanding: confirmed `getChairStats` is only used by `appGetNotification` (not by owner sales/distance, so no cross-endpoint coupling), and that a pure read-side rewrite avoids the transactional risk a write-side denormalized counter would carry.

## Change

- `webapp/go/app_handlers.go`: rewrote `getChairStats` to a single query:
  ```sql
  SELECT COUNT(*) AS total_rides_count, COALESCE(SUM(r.evaluation), 0) AS total_evaluation
  FROM rides r
  WHERE r.chair_id = ?
    AND EXISTS (SELECT 1 FROM ride_statuses rs WHERE rs.ride_id = r.id AND rs.status = 'ARRIVED')
    AND EXISTS (SELECT 1 FROM ride_statuses rs WHERE rs.ride_id = r.id AND rs.status = 'CARRYING')
    AND EXISTS (SELECT 1 FROM ride_statuses rs WHERE rs.ride_id = r.id AND rs.status = 'COMPLETED')
  ```
  This is semantically identical to the previous per-ride Go loop (same three-status presence check, order not checked), so no behavior change — only a query-shape/round-trip change.
- `webapp/sql/1-schema.sql`: added additive index `ride_statuses_ride_id_status_idx (ride_id, status)` to support the `EXISTS` lookups and the existing `owner_handlers.go` COMPLETED-status join.
- Commit: `9feff84 collapse getChairStats N+1 into single EXISTS query`.
