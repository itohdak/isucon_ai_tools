## Hypothesis
The icon route is the highest-volume route in the app; every request paid BEGIN + 2 SELECTs + ROLLBACK on the DB and a blob transfer. Icons change only via `postIconHandler`, users are insert-only, so both can be cached in-process; and the client (bench) may send `If-None-Match: "<icon_hash>"`, for which the spec permits an immediate 304.

## Change
`webapp/go/user_handler.go`: `getIconHandler` rewritten: no transaction; `getUserModelByName` (cache `userByNameCache`, positive hits only); if `If-None-Match` is present and equals `"` + cached sha256 + `"` -> `304` (never 304 for non-conditional requests); otherwise `getIconImage` (cache `iconImageCache`; users without an icon row are cached as "use fallback" and served from a once-loaded in-memory `NoImage.jpg` via `c.Blob(200, "image/jpeg")`). `getIconHash` now accepts a `ctxGetter` (`*sqlx.Tx` or `*sqlx.DB`). `postIconHandler` `Store`s hash and bytes after commit (readers `LoadOrStore`, so a stale concurrent read can never overwrite the writer's value; end state always converges to the new icon, well within the spec's 2s window). `clearUserCaches()` (called by `initializeHandler`) clears the two new caches too.
