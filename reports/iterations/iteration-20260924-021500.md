## Hypothesis
Same principle as iteration 5: an app-side cache that eliminates queries entirely (rather than making each cheaper) lowers s2 load AND s1 CPU (round trips + row scanning). users/themes are immutable after insertion, so cache invalidation is trivial (only `initialize`).

## Evidence
slp: 90523 themes + 90222 users-by-id queries per window (~19s of isupipe DB time, the largest single isupipe lever); pprof: sqlx/DB syscalls dominate app CPU; app code grep: no writers besides register.

## Change
`webapp/go/user_handler.go`: `userModelCache`, `themeModelCache` (`sync.Map`), `getUserModelByID()`, `getThemeModel()`, `clearUserCaches()` (also clears `iconHashCache`); `fillUserResponse` uses `getThemeModel`. `livecomment_handler.go` (commenter + reporter), `livestream_handler.go` (`fillLivestreamResponse` owner), `reaction_handler.go` use `getUserModelByID` instead of `SELECT * FROM users WHERE id=?`. `main.go` `initializeHandler` calls `clearUserCaches()`. Only successful reads are cached (ErrNoRows never cached). `getMeHandler` (session lookup) and name-based lookups deliberately unchanged.
