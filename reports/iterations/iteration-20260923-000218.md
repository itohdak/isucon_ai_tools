## Hypothesis

Per `docs/resource-scaling-policy.md`, an instance split is only justified when benchmark-time resource evidence shows a real bottleneck. The Resource Monitor Agent's Netdata data showed `s1` (app+db combined, 2 vCPUs) hitting 0% CPU idle at peak with a load average of 4.4 (avg) to 10.5 (peak) — 2-5x its core count. Follow-up `pidstat -u 1 90` sampling during a fresh benchmark run isolated the cause precisely: `mysqld` averaged **97.7% CPU** (essentially saturating one full core continuously) versus `isuride` (the Go app) at **42.97%** and `nginx` at 6.37%. This matched the Resource And Split Policy's explicit criterion "MySQL CPU is saturated and route/slowlog evidence shows DB time dominates," justifying a split.

## Decision

**Split accepted, but flagged as not yet fully stable.** The resource evidence and benchmark scores support the split as a net win — `s1` is no longer CPU-starved and typical scores are higher — but the one `CODE=32` failure is a new failure mode this session hadn't seen before, and a failing run is worse than a merely-lower-scoring one in a real contest. Working theory: `isuride-matcher.service`'s fixed cadence (one match per 0.5s tick) was implicitly paced by `s1`'s prior CPU contention; with that bottleneck removed, the app can generate ride-matching demand faster than the matcher can keep up during bursts, occasionally exceeding the benchmark's matching-latency tolerance. This is not a correctness bug introduced by the split itself — it is a previously-latent throughput limit newly exposed by removing the CPU bottleneck.

Kept the split live (rolling it back would just restore the original, worse CPU-bound state) but did not yet attempt a matcher throughput fix, since that would be a "matching strategy" change requiring separate human sign-off per `AGENTS.md`, and this iteration was already a large, multi-step infrastructure change.
