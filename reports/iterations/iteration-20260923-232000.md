# Iteration 7 — ISUCON13 (ISUPipe): Icon conditional-GET/ETag support (REJECTED — reverted)

## Agents Used

Reused iteration 5's App Understanding Agent finding (`getIconHandler` ignores `If-None-Match` entirely; described the exact safe-fix shape and invariants). Sub-agents were not used for implementation/verification because: the correctness analysis was already complete and specific (current behavior, safe fix, invariants, risk rating all given in iteration 5's dispatch); this iteration only needed implementation + verification, and the regression this iteration found was a *performance* effect the App Understanding Agent's correctness-focused analysis wasn't asked to predict (it correctly rated correctness risk low-medium and was right about that — the change was byte-for-byte correct per manual testing, just slower).

## Hypothesis

`getIconHandler` (`user_handler.go`) always returns `200` with the full image blob, ignoring `If-None-Match` entirely, even though `isupipe.md`'s manual explicitly allows (MAY) a conditional-GET 304 response keyed on the icon's SHA256 hash (same value as the `icon_hash` field other endpoints already return, computed in `fillUserResponse`). Adding this should reduce bytes transferred for repeat icon fetches without any correctness risk, since the manual's MUST NOT (never 304 an unconditional request) and MUST (200+fresh bytes on mismatch, 2s reflection) are straightforward to satisfy by computing the hash fresh from the DB on every request (no caching layer).

## Evidence (before change)

- Iteration 5's Profiler Agent: `GET /api/user/:username/icon` was the highest-*count* route (18,732 calls in the profiled window) though cheap per-call (avg 7.1ms) — a plausible target for reducing transferred bytes at that volume.
- Direct code read confirmed `getIconHandler` never reads `If-None-Match` and always does `c.Blob(200, ...)` (or `c.File(fallbackImage)` when no icon row exists).
- `fillUserResponse` already computes `iconHash := sha256.Sum256(image)` the same way for the `icon_hash` API field, confirming the hash definition to reuse.

## Change (implemented, then reverted)

Rewrote `getIconHandler` to: fetch the image (DB row, or read the fallback file into memory if none), compute `sha256.Sum256(image)` **unconditionally** (needed to know whether to 304, since freshness must be re-checked every request), compare against a trimmed `If-None-Match` header if present, return `304 Not Modified` on an exact match, otherwise set an `ETag` response header and return `200` with the full blob as before. `go build`/`go vet`/`gofmt -l` clean.

Files changed: `webapp/go/user_handler.go`.

## Verification

Codex verified directly (build/vet clean). First did a manual curl-based correctness check on `s1` directly against the Go app (bypassing nginx/DNS): unconditional GET → 200; GET with matching `If-None-Match` → 304; GET with a bogus `If-None-Match` → 200. All three matched the manual's required behavior exactly — the fix is correct.

Then ran 3 benchmark runs:

| Run | Score | Pass |
| --- | --- | --- |
| 1 | 11090 | true |
| 2 | 11097 | true |
| 3 | 11041 | true |

Average: **11076** — a tight, low-variance cluster (unlike most of this session's noisier swings), but consistently **~9.6% below** iteration 5's average of 12248.3 (and iteration 6's confirmation run of 11903 at the same pre-icon-fix commit). The tightness of the 3 values (11041-11097, a 56-point spread) rather than the session's usual 500-1500+ point run-to-run swings suggested a real, systematic effect rather than noise, so a same-conditions A/B (revert and re-run) was done to confirm.

**Root-cause theory:** the fix computes `sha256.Sum256(image)` on **every** `getIconHandler` call, unconditionally — including the large majority of calls that don't send `If-None-Match` at all and therefore get zero benefit from the hash computation (the benchmark client evidently does not send conditional requests often enough to offset this cost). At 18,732 calls/run (the highest-count route in the app, per iteration 5's Profiler data) and `s1` already confirmed CPU-saturated (iteration 5's Resource Monitor Agent), adding a SHA-256 hash of every served icon on every request is enough extra CPU work to measurably reduce overall throughput, outweighing the (apparently rarely-exercised) bandwidth savings from 304s. Reverted (`git revert --no-edit 7195190`, commit `8aaa23d`), redeployed, and re-benchmarked: **11902** (single run), consistent with iteration 5/6's range — confirms the revert restores the prior performance.

Not re-attempted this session given diminishing iteration budget; noted for a future session.
