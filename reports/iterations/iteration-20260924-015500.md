## Hypothesis
`fillUserResponse` (on nearly every hot path) fetched the whole icon BLOB and sha256'd it per call. With the DB commit path already cheaper and s1 now at ~87% busy, removing that cost should help both hosts: s1 loses the hash (35.6% of app CPU) and s2 loses ~64k queries (13s of DB time) per window. Differs from the rejected session-2-iteration-1 DB-column variant (`icons.icon_hash`): that still issued one query per call and ran while s1 had 44% headroom and s2 was the only bottleneck; a cache removes the query entirely, and the host balance has since changed.

## Evidence
pprof + netdata + slp numbers above; baseline 29014 (iteration 4).

## Change
`webapp/go/user_handler.go`: `iconHashCache sync.Map` (user id -> hex sha256), `getIconHash()` used by `fillUserResponse` (readers `LoadOrStore`, fallback image handled as before); `postIconHandler` `Store`s the new hash after `tx.Commit()`. `webapp/go/main.go`: `initializeHandler` clears the cache after init.sh (users/icons are truncated and ids reused). Concurrency reasoning: single app process; a reader that read the pre-commit image can only LoadOrStore (never overwrite) so the writer's post-commit Store always wins; if the reader stores first the writer overwrites. Output (`icon_hash` JSON field) is bit-identical to before.
