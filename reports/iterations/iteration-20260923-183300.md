## Hypothesis

Phase 2 of the matching redesign the user originally requested: replace the batch matcher's greedy oldest-ride-first assignment (each ride locks its single best chair unconditionally, which can force a worse match onto the next ride even when a swap would reduce total cost) with a global-optimum assignment across the whole fetched batch, using a cost function that also incorporates ride wait time as an urgency term — per the user's own suggestion ("マッチング時間がネックになる場合は、それに寄与するコストも追加すればよい") — so CODE=32 avoidance is built into the objective rather than relying only on hard sequential priority.

## Change

`webapp/go/internal_handlers.go` + new `webapp/go/matching_assignment.go` (commit `7a2f8fc`):
- Added a self-contained Hungarian algorithm (`hungarianAssignment`, O(n²·m), no external dependencies) solving the rectangular minimum-cost bipartite assignment problem for n rows (rides) ≤ m columns (chairs).
- `matchPendingRides` now builds an n×m cost matrix from the same two batch SELECTs as before (up to `maxMatchesPerCall=10` oldest unmatched rides, all free chairs) and calls `hungarianAssignment` instead of the previous per-ride greedy sort-and-pick loop.
- New cost function: `matchCost(chair, ride, now) = pickupCost * (1 + urgencyWeight * waitSeconds)`, where `pickupCost` is the original `distance/speed` estimate and `urgencyWeight = 0.1` (a ride waiting 10s has ~2x effective cost, 30s ~4x, 100s ~11x), biasing the optimizer toward protecting long-waiting rides.
- When free chairs are scarcer than fetched rides, rides are truncated to the oldest `len(available)` (already ordered by `created_at ASC`) before optimizing, satisfying the algorithm's `n ≤ m` requirement while preserving the same anti-starvation intent as before.
- `matching_assignment_test.go`: unit tests including 200 random trials cross-checked against brute-force optimal (n≤4, m≤7), plus hand-verified square/rectangular/urgency-preference/single-row cases. All pass.
