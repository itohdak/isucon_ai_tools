## Hypothesis

`getUserStatisticsHandler`/`getLivestreamStatisticsHandler` (`webapp/go/stats_handler.go`) each build a ranking by looping over **every** user (1186) / livestream (7578) in Go and issuing 2 SQL queries per row (2373 / 15157 round trips per single stats API call). Replacing this with one aggregate `GROUP BY` query per ranking (reactions count and tip sum, both LEFT-JOINed onto the full user/livestream list) should collapse each stats call from thousands of round trips to 2 total queries, while preserving the exact same downstream Go sort/tie-break/rank-scan logic unchanged.

## Evidence (before change)

- SQL Agent's iteration-1 ranking: `SELECT IFNULL(SUM(l2.tip),0) FROM users u JOIN livestreams l JOIN livecomments l2 WHERE u.id=?` (922 calls/21.98s sum) and the matching reaction-count query (920 calls/21.14s sum) were the #4/#5 largest total-query-time contributors even after iteration 1's indexes.
- Manual measurement after deploying the fix: `GET /api/user/:username/statistics` average latency with the OLD code (reverted, measured directly via `journalctl`) was **~6.2s avg, up to 7.8s worst-case**, over a 4-minute sample — versus ~30ms with the new aggregate code. The per-call speedup was real and large (~200x).

## Change (implemented, then reverted)

Rewrote both handlers' ranking-construction loops to issue one `LEFT JOIN`ed, `GROUP BY`-aggregated query (via two derived tables, one for reaction counts and one for tip sums, keyed by `user_id`/`livestream_id` respectively) instead of looping per-row with 2 queries each. Verified via `EXPLAIN` that both derived-table subqueries use the iteration-1 indexes (`type=index`/`ref`, no `Using temporary`/`Using filesort`) and that the whole aggregate query runs in 22-32ms standalone. The Go-side sort/tie-break/rank-scan code (the part flagged as highest correctness risk by App Understanding Agent) was left completely untouched — only the data-fetching step changed. `go build`/`go vet`/`gofmt -l` all clean.

Files changed: `webapp/go/stats_handler.go`.

Commits: `22d647c` (the fix) then `fb4b562` (the revert, restoring the exact pre-iteration-2 file), both on the `isucon13_practice_3` repo, both pushed successfully.

No new error signatures traced to the changed code itself (`journalctl` showed zero occurrences of "failed to aggregate user scores" / "failed to aggregate livestream scores" — the handler never errored). The 500s/timeouts present in both sets of runs were the same pre-existing signatures from iteration 1 (end-of-run `context canceled` cancellations, one intermittent icon-POST deadlock, occasional DNS UDP timeouts, one report-fill race) — not new.

**Root-cause theory (not fully proven, flagged for a future targeted test):** `main.go` sets `db.SetMaxOpenConns(10)` — only 10 MySQL connections total for the whole app. With the old, slow stats handler, each stats call held a connection for 6+ seconds, which likely acted as an *unintentional throttle* on the bench workers' overall request-issue rate (a worker blocked on its own stats call can't simultaneously hammer other endpoints). Making stats calls ~200x faster removed that throttle, letting bench workers cycle through the same 10-connection pool far more often — which plausibly increased contention/queueing on other paths (icon serving, moderation, reservation) enough to reduce total completed high-value traffic (tips/livecomments) more than the stats fix itself saved. This would mirror the ISUCON14 session's documented lesson (recorded in the App Understanding Agent skill doc) that a fixed-rate/fixed-capacity component can be implicitly pacing the whole system, and "speeding up" one path without addressing the shared bottleneck it was masking can make the *system* net slower even though that one path got faster. Not chasing this theory further this iteration — flagged as the next candidate (see below) since it points at `SetMaxOpenConns` as a promising, low-risk, single-line lever now that per-query time is under control.

## Benchmark Result

Regression confirmed and reproducible: **avg 6550.5** (stats fix) vs **avg 8915** (reverted state, measured later in the same session) — a clear, consistent ~26% drop attributable to the stats-handler change. **Rejected and reverted.**

(Note: the reverted-state score of 8915 avg is itself notably higher than iteration 1's own initial 3-run average of 7492.7 on the identical index-only code — see the theory above; this within-session upward drift on unchanged code is consistent with the Verifier skill doc's documented "run-to-run swings" and reinforces why the A/B was necessary to isolate the real effect of the stats-handler change specifically, rather than trusting either measurement in isolation.)

## Next Candidate

Test `db.SetMaxOpenConns(10)` in isolation: raise it (e.g. to 30-50, informed by `SHOW GLOBAL VARIABLES LIKE 'max_connections'` on s1's MySQL, which defaults much higher) while keeping the stats handler in its current, reverted (slow) state, to check whether connection-pool headroom alone changes the score — this isolates the pool-contention variable before re-attempting the stats fix. If a larger pool alone helps, the natural follow-up is reapplying the stats aggregation fix *together with* a larger pool, since removing 2371+ wasted round trips is unambiguously less total DB work and should be a net win once the pool ceiling stops being the limiting factor. This is a pure application-level config change (`SetMaxOpenConns` in Go code), not an instance resource change, so it stays within the Resource And Split Policy.
