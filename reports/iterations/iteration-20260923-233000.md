# Iteration 8 — ISUCON13 (ISUPipe): Fix fillLivestreamResponse per-tag N+1

## Agents Used

Reused iteration 5's App Understanding Agent finding (confirmed `fillLivestreamResponse` issues one `SELECT * FROM tags WHERE id = ?` per tag per livestream, rated an easy, low-risk batch target with "no subtle invariant beyond preserving tag order/fields"). Sub-agents were not used for implementation/verification because: the finding was already specific and low-risk, and this is a narrow, single-function change matching the existing `sqlx.In` pattern already used elsewhere in the same file (`searchLivestreamsHandler`), reducing implementation risk further.

## Hypothesis

`fillLivestreamResponse` (`livestream_handler.go`, called for every livestream shown in any listing/detail endpoint — search, my-livestreams, user-livestreams, get-by-id) fetches a livestream's tags via `SELECT * FROM livestream_tags WHERE livestream_id=?` (already indexed since iteration 1), then loops over each tag row issuing a separate `SELECT * FROM tags WHERE id=?`. Since `tags` is a small, mostly-static reference table, batching all tag lookups for one livestream into a single `SELECT * FROM tags WHERE id IN (...)` query (reassembling results in the original per-tag order in Go) should be strictly less total work with an identical response.

## Evidence

- Direct code read confirmed the loop at `livestream_handler.go` lines ~501-511 (pre-fix): one `tx.GetContext(... "SELECT * FROM tags WHERE id = ?" ...)` per `livestreamTagModels[i]`.
- Iteration 5's SQL Agent slow-log sample showed `SELECT * FROM tags WHERE id=N` at 16,401-12,000 calls across different sampling windows — one of the highest-*count* query shapes in the app (though individually cheap, ~0.3-0.35ms avg, since `tags` is tiny and PK-indexed) — confirms this is a very frequently-hit N+1, even if not top-ranked by total time.
- The existing `sqlx.In(...)` + `tx.SelectContext(ctx, &dst, query, params...)` pattern (no `Rebind` needed, confirmed by an existing identical usage in `searchLivestreamsHandler` a few hundred lines above in the same file) was reused verbatim for consistency and lower risk.

## Change

Batched the per-tag loop into: collect all `tag_id`s for the livestream, one `sqlx.In("SELECT * FROM tags WHERE id IN (?)", tagIDs)` query, build a `map[int64]*TagModel`, then reassemble the `tags` slice by iterating `livestreamTagModels` in its original order and looking up each tag from the map — preserving both tag content and original ordering exactly. Guarded with `if len(livestreamTagModels) > 0` to avoid an `IN ()` query with an empty slice. `go build`/`go vet`/`gofmt -l` clean.

Files changed: `webapp/go/livestream_handler.go`.
