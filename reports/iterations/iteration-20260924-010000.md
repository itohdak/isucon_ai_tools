## Hypotheses

1. **Search tag-filter N+1** (`searchLivestreamsHandler`): one `SELECT * FROM livestreams WHERE id=?` per matched `livestream_tags` row -> single `IN (...)` query, reassembled in original order (duplicates preserved). Reduces s2 query count.
2. **Re-test `CREATE INDEX nametype_index ON isudns.records(name,type)`** -- session 1 rejected it (benchmark's adaptive DNS attacker escalated) but that was when s1 was CPU-saturated and hosted mysqld. Now s1 has headroom and the records full scans are the biggest single cost cluster on s2.

## Evidence

- **Environment noise discovered mid-iteration**: the freshly recreated instances run Ubuntu's `unattended-upgrade` (apt-daily-upgrade) shortly after boot. On s1 it burned ~92% of a core during the first post-fix runs; on s2 a full upgrade (mysql-server, systemd, kernel, nginx, libc...) ran for 25+ minutes at 35-97% CPU. Runs during this window: 16086 (Resource Monitor's, also concurrent with SQL Agent's slp), 25523, 24473, 19230 -- all invalid for A/B. Fixed by disabling `unattended-upgrades.service`, `apt-daily.timer`, `apt-daily-upgrade.timer` on s1 and s2 and gracefully SIGTERM-ing the running upgrade (it finishes the current dpkg batch then stops; `dpkg --audit` clean afterwards, mysql active). Both deploy scripts were re-run afterwards to reassert tracked config.
- Clean A/B (same environment, back-to-back, both hosts idle of upgrade noise): fix (`eca2362`) 26084 / 25629 / 25217 (avg 25643) vs control old handler (`b1e926d`) 26934 / 26033 / 25102 (avg 26023). Indistinguishable (spread ~ +/-1000). The search route is only ~245 calls per run; its cost is dominated by per-item `fillLivestreamResponse` (~5 queries per livestream), not the tag lookup.
- Index re-test (live `CREATE INDEX`, later dropped): EXPLAIN switched from `ALL`/1486 rows to `ref`/1 row, but 23191 / 24392 / 24693 (avg 24092) vs control ~25800; bench.log shows `DNS水責め負荷が上昇します` up to `parallelis: 4` and `DNSAttacker並列数: 4`. The benchmark escalates DNS attack load as DNS gets faster; the extra load (pdns on s1 plus the resulting isudns lookups on s2) costs more than the index saves.
