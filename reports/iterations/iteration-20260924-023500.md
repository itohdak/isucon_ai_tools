## Hypothesis
Reservations hold whole-table locks and do 3 full scans of `reservation_slots` per call; making the predicate sargable removes ~1.67M examined rows per window on s2 and shortens/narrows lock hold times so concurrent reservations stop serializing.

## Evidence
SQL Agent EXPLAIN/rows-examined numbers above; route avg 162ms.

## Correctness
`end_at <= E` and `start_at < end_at` (true for every valid slot; every slot is 3600s) imply `start_at < E`, so adding `start_at < E` cannot change the matched row set. The per-slot `SELECT slot ...` ran in the same transaction right after the `FOR UPDATE` read of that same row and before any write, so it returned the same value as `slot.Slot`. Overbooking protection is preserved: two overlapping reservations still contend on the X record locks of the shared slots.

## Change
`webapp/go/livestream_handler.go` `reserveLivestreamHandler`: `... AND start_at < ?` (bound to `req.EndAt`) added to the `FOR UPDATE` select and the `UPDATE`; `count := slot.Slot` replaces the per-slot re-query.
