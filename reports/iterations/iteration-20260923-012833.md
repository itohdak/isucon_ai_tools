## Preliminary Work: Netdata On `s3`

(Carried over context, not new this iteration — see `reports/iterations/iteration-20260923-005833.md` for the Netdata setup that made the precise before/after CPU/load measurements below possible.)

## Hypothesis

Implementing the SQL Agent's top two findings (disable binlog + relax commit fsync; add a covering index for the hottest query) should measurably reduce `s3`'s MySQL CPU cost, hopefully creating enough headroom to safely raise `maxMatchesPerCall` beyond 3 (which had been confirmed to fully saturate `s3`'s CPU at `maxMatchesPerCall = 5`).

## Change

1. `s3/etc/mysql/mysql.conf.d/mysqld.cnf`: added `skip-log-bin` (MySQL 8.0 enables binary logging by default even with no explicit `log_bin` directive, so this needed to be explicit) and `innodb_flush_log_at_trx_commit = 2`. No replication/PITR need on this practice host (DB is reset via `/api/initialize` between runs), so the only trade-off is losing up to ~1s of writes on an OS/mysqld crash — acceptable for a benchmark host.
2. `webapp/sql/1-schema.sql`: replaced `ride_statuses_ride_id_created_at_idx (ride_id, created_at)` with a covering `ride_statuses_ride_id_created_at_status_idx (ride_id, created_at, status)`, so the ~29k-call/run latest-status lookup becomes index-only instead of requiring a clustered-index lookup per call.
3. Commit: `ec8b776 reduce s3 MySQL CPU cost: disable binlog, relax commit fsync, covering index`.

## Verification

- Deployed config to `s3` directly (restarted `mysql.service`), confirmed new values (`log_bin=OFF`, `innodb_flush_log_at_trx_commit=2`) took effect.
- **Process note**: initially forgot to `git pull` on `s1` before re-triggering `/api/initialize`, so the first initialize call still applied the *old* schema — caught this by checking `SHOW INDEX FROM ride_statuses` on `s3` and seeing the old 2-column index name, pulled on `s1`, and re-ran `/api/initialize` to confirm the new 3-column covering index was actually created.
- **Confirmed the fsync fix worked as intended**: post-tuning slow log shows `COMMIT` averaging **0.07ms** (3769 commits, 0.26s total) vs. the pre-tuning finding of ~1.25ms average (30,667 commits, 38.49s total) — roughly an **18x reduction** in per-commit overhead.
- **However, `s3`'s CPU is still fully saturated at peak load.** Queried Netdata for the exact window of a post-tuning benchmark run (2026-09-22T16:26:22–16:27:30 UTC): CPU idle dropped to **0.1-0.9%** for the sustained middle of the run (same as pre-tuning), with `iowait` now negligible (confirming the fsync/IO-wait component really was removed) but `user`+`system`+`softirq` CPU alone fully occupying both vCPUs.
- 3 benchmark runs post-tuning: score 10162 (`map[8:1]`), 10352 (`map[]`), 9856 (`map[]`) — all `pass=true`, but not clearly higher than the pre-tuning `maxMatchesPerCall=3` baseline (12927, 10595, 12519, 12684, 12667 from the previous iteration). Given this session's established noise band, 3 samples isn't enough to call this conclusively neutral vs. slightly negative, but it is clearly **not** the large improvement hoped for.

## Decision

**Keep the DB tuning changes** (both are safe, verified-correct improvements on their own terms — the commit-overhead reduction is real and large, and the covering index is a pure win with no downside), **but the underlying goal (creating CPU headroom for a bigger matcher batch) was not achieved.** Removing the fsync/binlog bottleneck simply let other CPU-bound work (most likely the matcher's chair-selection query, per the SQL Agent's finding #3, which scales with both batch size and active-chair count) immediately fill the freed capacity — another instance of this session's recurring pattern where fixing one bottleneck exposes the next rather than proportionally increasing overall headroom.

**Do not attempt to raise `maxMatchesPerCall` above 3 again** without first addressing the matcher's chair-selection query cost directly (SQL Agent's finding #3: the correlated `NOT EXISTS(...NOT EXISTS...)` "chair has no unfinished ride" check re-executes once per active chair per call). A real fix there needs an app-maintained "chair is free" flag (a code change to matching-adjacent logic, not a pure DB-side tune), which is a bigger, higher-risk change requiring the same explicit approval process used for the DB split and the matching-strategy fix.

## Next Candidate

This is a matching-strategy-adjacent change and should go through the same explicit-approval step as prior matching changes.
